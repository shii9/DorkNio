01 — Mental Model

Every Page Has Layers. Every Operator Scans One.

This is the core concept. A webpage isn't a single blob of text — it has distinct structural layers. Each dork operator is designed to search exactly one specific layer. Once you understand this, nothing will feel confusing again.

Key Insight
intitle: and intext: are the most commonly confused pair. Remember: intitle: reads the invisible metadata tag (what the developer named the page for SEO/browser purposes). intext: reads the actual words a visitor sees when they open the page. They can be completely different — a login page title might say "Secure Portal" while the body says "Enter your admin password".

03 — Inside the Page

What Each Operator Actually Reads

Here is a full browser mockup of a real-style page — every element annotated to show exactly which operator scans which part of the HTML structure.

Admin Login — Target.com Security Panel
← intitle: reads this
https:// target.com /admin/login.php ?id=1&redirect=dashboard ← inurl: reads all of this
Welcome to the Admin Panel ⚠ This is <h1> — NOT what intitle: scans
Please enter your username and password to continue. Default credentials are admin / admin. If you are locked out, contact your system administrator. This panel controls all user accounts, logs, and server configuration. ← intext: scans all visible text here
Sign In
Forgot your password?  |  Click here to register  |  Reset admin credentials ← inanchor: scans these link texts
intitle:
Reads: "Admin Login — Target.com Security Panel" — the browser tab text. This is the <title> tag in HTML head. The visible <h1> "Welcome to the Admin Panel" is a completely separate element — intitle: ignores it.
inurl:
Reads: "target.com/admin/login.php?id=1&redirect=dashboard" — the full address. Matches against any part: inurl:/admin/, inurl:login.php, inurl:"?id=", or inurl:redirect all match this URL.
intext:
Reads: all visible paragraph text — "username", "password", "admin/admin", "system administrator" etc. If it's rendered on screen, intext: finds it. Perfect for locating exposed credentials, error messages, or config values.
inanchor:
Reads: "Forgot your password?", "Click here to register", "Reset admin credentials" — only the visible text of the <a> links. Not the href URLs — the human-readable label text.
Critical Distinction — intitle: vs intext:
The <title> tag and the <h1> heading are independent. A developer sets the title tag for SEO and browser display; the h1 is the visible page heading.

intitle: only reads the <title>. The h1 is part of the body — intext: reads it, not intitle:.
04 — Operator Guide

Complete Operator Reference

All operators organized into four categories: Layer Targeting, Scope & Type Filters, Google Meta Operators, and Boolean & Syntax Modifiers. Each card includes single vs. all behavior, practical security examples, and copy-ready dorks.

Category A
Layer Targeting Operators
4 operators + all- variants

These operators target a specific structural layer of a webpage — the HTML title tag, the URL, the visible body text, or the anchor link text. Each one locks your keyword to exactly one layer. Master these first; they're the backbone of every effective dork.

🔵
intitle:   /   allintitle:
Scans → HTML <title> tag (browser tab text)
Title Tag

Searches the <title> HTML element — the text that appears in the browser tab and as the blue clickable heading in Google results. Developers set this tag for SEO purposes, so it typically reveals the true purpose of a page.

Important: This is NOT the visible <h1> or <h2> heading rendered inside the page. Those two things are completely separate. The title tag lives in <head>; the h1 lives in <body>.

Single vs. All — The Key Difference
intitle: One word must be in title
intitle:admin login
"admin" must be in the <title> tag.
"login" can be anywhere — title, body, URL, anywhere on the page.

Result: broad — catches more pages.
allintitle: All words must be in title
allintitle:admin login
Both "admin" AND "login" must appear in the <title> tag.
Neither word is allowed to be elsewhere — both must be in the title.

Result: narrow — more precise, fewer results.
Rule: With intitle:, only the first word is locked to the title — the rest float freely anywhere.
With allintitle:, every word is locked to the title — nothing floats.
Real Security Examples
intitle:"index of" "parent directory"
Finds open directory listings — web servers with directory browsing enabled. Classic for finding exposed file repositories.
intitle:"phpMyAdmin" inurl:"/pma/"
Finds exposed phpMyAdmin database interfaces. intitle: confirms it's phpMyAdmin; inurl: confirms the /pma/ path.
allintitle:admin control panel site:target.com
All three words must be in the title — highly specific. Only returns pages where the developer explicitly titled it with all those terms.
intitle:"Kibana" inurl:":5601"
Finds exposed Kibana data dashboards running on port 5601 — often left open without authentication.
🟢
inurl:   /   allinurl:
Scans → Full URL — path, filename, query parameters
URL

Searches within the URL string — matches against any part of the address: subdomain, directory path, filename, or query parameter key/value. This is typically the most powerful operator for finding specific admin endpoints, vulnerable parameters, or exposed paths.

URL breakdown: https://target.com/admin/edit.php?id=1 — inurl: matches anything in the highlighted portions.

Single vs. All — The Key Difference
inurl: One term must be in URL
inurl:admin login
"admin" must be somewhere in the URL path.
"login" can be in the URL, title, body, or anywhere.

Matches: /admin/home, admin.php, /users/admin etc.
allinurl: All terms must be in URL
allinurl:admin login php
All three terms must appear within the URL.
URL like /admin/login.php matches — all three terms present.

Result: very specific, few results.
Rule: inurl:admin login — only "admin" is required in URL. "login" floats anywhere.
allinurl:admin login — both "admin" AND "login" must be in the URL itself.
Real Security Examples
inurl:/wp-admin/ site:target.com
Finds WordPress admin login pages on a specific target. Extremely common CMS attack surface.
inurl:"?id=" site:target.com
Finds pages with an integer parameter — classic SQLi attack surface. The ?id= suggests unsanitized database query input.
inurl:".php?file=" site:target.com
URL parameter named "file" — classic Local File Inclusion (LFI) attack vector. Suggests a PHP file is loading content by filename from user input.
allinurl:admin config php site:target.com
URL must contain admin, config, and php — very specific. Targets admin configuration PHP files directly.
🟡
intext:   /   allintext:
Scans → All visible page body text content
Body Text

Searches all visible text rendered in the page body — paragraphs, error messages, labels, headings, table content, form text, and any other human-readable output. If a person visiting the page can read it, intext: can find it.

Note: By default, Google already searches body text for plain keyword queries. The power of intext: comes from combining it with other operators — locking a term to the body while using inurl: or filetype: to narrow by structure.

Single vs. All — The Key Difference
intext: One word must be in body
intext:"password" inurl:config
"password" must appear in the page body text.
"config" must appear in the URL.

Both are independently locked to their respective layers.
allintext: All words must be in body
allintext:username password database
All three words must appear in the body text of the same page.
None can be in just the URL or title — all locked to body content.

Good for finding credential exposure.
Rule: intext:username password — only "username" is locked to body; "password" floats anywhere.
allintext:username password — both must appear in the page body specifically.
Real Security Examples
intext:"DB_PASSWORD" intext:"DB_HOST" filetype:env
Finds exposed .env config files containing both DB_PASSWORD and DB_HOST in their content — direct database credential exposure.
intext:"sql syntax near" intext:"mysql_fetch"
Finds pages leaking MySQL error messages — both strings appearing together strongly signals an SQLi vulnerability.
intext:"Fatal error" intext:"stack trace" site:target.com
Finds pages with application stack traces — these leak internal file paths, function names, and sometimes credentials.
allintext:username password login filetype:log
All three words must be in a log file's content — finds log files with plaintext credential dumps.
🟣
inanchor:   /   allinanchor:
Scans → Clickable hyperlink text (<a> tag visible label)
Anchor Text

Targets the visible text of hyperlinks — what you actually click on, not the URL those links point to. For example, in <a href="/admin">Click here to access admin</a>, inanchor: reads "Click here to access admin", not "/admin".

Use case: Finding pages that are linked using specific keywords, mapping navigation structures, or discovering hidden admin sections that are linked from public pages but not directly indexed.

Single vs. All — The Key Difference
inanchor: One word must be in link text
inanchor:"admin login"
The phrase "admin login" must appear as anchor text in at least one link on the page.

Finds pages that have a link literally labeled "admin login".
allinanchor: All words must be in link text
allinanchor:admin control panel access
All four words must appear in anchor text on the page.

Very specific — only pages with a link labeled something like "Admin Control Panel Access".
Clarification: inanchor: is about anchor text on the page — the link label text. It is not searching where the link points to (that would be inurl:). It reads the human-readable clickable text of the <a> element.
Real Security Examples
inanchor:"reset password" site:target.com
Finds pages with "reset password" links — useful for mapping authentication flows and finding unlinked password reset pages.
inanchor:"admin panel" inurl:admin site:target.com
Pages with "admin panel" anchor text AND /admin in URL — triangulates high-confidence admin pages.
Category B
Scope & Type Filters
site:  ·  filetype:  ·  ext:

These operators don't search page content — they constrain scope. site: limits results to a domain. filetype: (and its identical alias ext:) limits results to a file type. Always combine these with Category A operators for precision.

🔴
site:
Scope → Restrict all results to a specific domain or subdomain
Domain Scope

Restricts every result in the query to a specific domain. It is the most-used operator in penetration testing recon. It is not a text search — it doesn't look inside page content. It is a scope filter that limits the domain Google will return results from.

Subdomain behavior: site:target.com includes all subdomains (api.target.com, mail.target.com, dev.target.com). To scope to one subdomain only, be explicit: site:dev.target.com.

No "allsite:" variant exists.

Real Security Examples
site:target.com -www
All results from target.com excluding the main www subdomain — enumerates dev, api, staging, mail, and other subdomains.
site:target.com intitle:"index of"
Finds open directory listings across the entire target domain. One of the most valuable recon dorks.
site:*.target.com
Wildcard subdomain enumeration — the asterisk forces Google to show results from all discovered subdomains separately.
site:gov filetype:xls intext:password
Finds government Excel files with "password" in the content — government domains are often misconfigured and expose documents.
🟠
filetype:   /   ext: identical alias
Filter → Restrict results to a specific file extension / MIME type
File Type

Restricts results to indexed files of a specific extension. filetype:pdf and ext:pdf are functionally identical — Google treats them the same. No "allfiletype:" variant exists.

High-value extensions for security research: env, sql, log, bak, conf, config, pem, key, txt, xml, json, yml, yaml, xls, xlsx, csv, php. Each extension has different leak potential.

filetype: vs ext: — Use Either
Both are accepted by Google and return identical results. filetype: is more widely documented; ext: is shorter to type. Some older resources use one or the other — they mean the same thing.
Real Security Examples — High-Value Extensions
filetype:env intext:"APP_SECRET" site:target.com
Exposed Laravel/Node .env files containing the application secret key — allows session forgery and cryptographic attacks.
ext:sql intext:"INSERT INTO" intext:"password"
Exposed SQL database dumps containing INSERT statements with password values — often plaintext or weakly hashed.
filetype:log intext:"username" intext:"password" site:target.com
Application log files containing username and password strings — authentication logs are a goldmine for credential harvesting.
filetype:pem intext:"PRIVATE KEY"
Exposed PEM files containing private keys — SSL certificates, SSH keys, or code-signing keys leaked to public web servers.
ext:yml intext:"password:" intext:"host:"
YAML config files (Docker Compose, Kubernetes, Rails database.yml) with credentials in plaintext.
Category C
Google Meta Operators
cache:  ·  related:  ·  info:

These operators don't search page content or structure. They query Google's own index metadata — its cached snapshots, its topical similarity graph, and its stored knowledge about URLs. They're recon operators, not content operators.

🗃
cache:
Meta → Shows Google's stored snapshot of a URL from its last crawl
Cache Index

Instead of loading the live page, cache: loads the version Google archived during its last crawl. The snapshot date is displayed at the top. No "allcache:" variant exists.

Security use cases: (1) View a page that has since been taken down or modified. (2) Access content when the live site is rate-limiting, firewalled, or blocking your IP. (3) Find pages that exposed sensitive data before admins removed them. (4) Compare cached vs. live versions to spot recent changes.

Limitation: Google is reducing cache availability — as of 2024, many sites no longer have cached versions. If cache: returns nothing, try the Wayback Machine at web.archive.org.

Usage Patterns
cache:target.com/admin
View Google's last snapshot of the /admin path — useful if it now redirects or returns 403.
cache:target.com/config.php
Check if Google cached a config file before it was locked down — may still show exposed credentials.
cache:target.com
Load the homepage snapshot — quick check on when Google last crawled the site.
🔗
related:
Meta → Returns websites topically similar to a given domain
Similarity Graph

Queries Google's topical similarity index to return websites it considers similar in content, purpose, or industry to the target domain. No "allrelated:" variant exists.

Security use cases: (1) Competitor infrastructure mapping — companies in the same space may share hosting, vendors, or technology stacks. (2) Finding affiliate, mirror, or partner sites associated with a target. (3) Passive recon without touching the target directly. (4) Bug bounty expansion — similar companies often have overlapping infrastructure or shared codebases.

Note: Works best on well-known domains. Lesser-known targets may return no results.

Usage Patterns
related:target.com
Returns sites Google considers similar — map the target's industry ecosystem and find potential affiliate domains.
related:target.com site:gov
Similar .gov domains — useful for scoping government contractor or supplier recon.
ℹ
info:
Meta → Displays Google's summary card about a specific URL
Knowledge Card

Shows a Google knowledge summary for a given URL — links to view its cached version, find similar pages, and see pages linking to it. Acts as a quick recon pivot point from a single known URL.

Security use cases: (1) Quick snapshot of what Google knows about a specific URL. (2) Discover related pages and inbound links that reveal the site's full index surface. (3) Useful as a starting point before deep-diving with other operators.

Note: info: functionality has been reduced in recent Google updates. Some features only appear for well-indexed domains.

Usage Patterns
info:target.com
Quick knowledge card — starting recon pivot. Shows cache link, similar pages, and linking pages.
info:target.com/admin/login.php
What does Google know about this specific path? Check if it's indexed and what metadata is available.
Category D
Boolean & Syntax Modifiers
"phrase"  ·  -minus  ·  OR  ·  *  ·  ..

These aren't operators — they're syntax modifiers that change how Google interprets your query. They apply across all operators. Master these alongside the layer operators and you can build surgical dorks with high signal-to-noise ratio.

" "
"exact phrase"
Modifier → Forces exact phrase matching, no synonyms or reordering
Exact Match

Wrapping a phrase in double quotes tells Google to match it exactly — no synonym substitution, no word reordering, no partial matches. This is critical when you're looking for specific error strings, config keys, or credential patterns that must appear verbatim.

Without quotes: Google may reorder words, use synonyms, and split the phrase across the page.
With quotes: The exact sequence of words must appear together in that exact order.

Combine with operators: intitle:"Admin Login" means the title tag must contain exactly "Admin Login" — not "Login Admin" or "Admin Panel Login".

Usage Patterns — Exact Phrases in Security Research
"index of /"
Exact Apache/Nginx open directory listing title — the precise format server auto-generated titles use.
"Warning: mysql_connect()"
Exact PHP MySQL error string — finds pages leaking database connection errors with host/credentials.
intitle:"index of" "parent directory"
Both exact phrases — title must contain "index of" AND body must contain "parent directory" (dir listing element).
"-----BEGIN RSA PRIVATE KEY-----"
The exact PEM header for RSA private keys — finds exposed private key files or pages with embedded keys.
filetype:env "DB_PASSWORD="
Exact config key in .env files — including the = ensures it's a variable assignment, not just a mention.
−
-keyword   /   -operator
Modifier → Excludes results containing the specified term or matching the operator
Exclusion

Prepend - (no space) to any keyword or operator to exclude results matching that term. Works globally — not just on keywords but on any operator: -inurl:, -intitle:, -site:, -filetype:.

Without exclusion: Broad queries return thousands of noisy, irrelevant results.
With exclusion: Systematically filter out false positives, known-safe pages, and irrelevant file types.

Critical technique: Chain multiple exclusions: -inurl:login -inurl:signup -intitle:404 removes the most common noise sources at once.

Usage Patterns — Noise Reduction
site:target.com -www -inurl:blog -inurl:help
Enumerate interesting subdomains while filtering out the main www site and known public-facing paths.
intitle:"index of" -inurl:wordpress -inurl:wp-content
Find open directories while excluding WordPress plugin/theme directories (most common false positives).
filetype:sql intext:"password" -site:github.com -site:pastebin.com
Find exposed SQL dumps while excluding the two biggest paste-site noise sources.
site:target.com -inurl:404 -intitle:"Page Not Found"
Exclude dead pages and error pages from domain enumeration results.
OR |
OR   /   | (pipe)
Modifier → Logical OR — returns results matching either term (OR must be uppercase)
Logical OR

Returns results that match either the left OR the right expression. The keyword OR must be uppercase — lowercase "or" is treated as a regular search word. The pipe character | is an identical functional alias.

Default Google behavior is AND — all keywords must appear. OR overrides this to allow either/or matching.

Use parentheses for grouping: (inurl:login OR inurl:signin) site:target.com — groups the OR expression before applying site: to both results.

Usage Patterns — Covering Multiple Variants
site:gov OR site:mil filetype:xls intext:password
Cover both government TLDs in one query — finds Excel files with passwords on .gov and .mil domains.
(inurl:login OR inurl:signin OR inurl:auth) site:target.com
Find all authentication endpoints by covering three common URL patterns in one query.
filetype:env OR filetype:conf OR filetype:cfg intext:"password"
Cover three common config file extensions simultaneously — triple the exposure surface in one query.
intitle:"phpmyadmin" | intitle:"phpMyAdmin"
Handle capitalization variants of phpMyAdmin titles using pipe — catches both naming conventions.
*
*  (wildcard)
Modifier → Matches any single word within a quoted phrase
Wildcard

Inside a quoted phrase, the asterisk * acts as a word-level placeholder — it matches any single word in that position. This is useful when you know the pattern but not the exact wording.

Important: The * only works inside quoted strings. Outside quotes it is treated as a regular character. It also matches exactly one word, not multiple words or zero words.

Key patterns: Directory listings ("index of *"), partial error messages ("error * database"), config blocks ("password * admin").

Usage Patterns — Pattern Matching
intitle:"index of *" site:target.com
Catches all directory listings — "index of /uploads", "index of /backup", "index of /admin" — one dork covers all variants.
intext:"error * mysql" site:target.com
Matches any MySQL error message pattern — "error in mysql", "error connecting mysql", etc.
"admin * password" filetype:txt
Matches "admin default password", "admin user password", "admin reset password" in plaintext files.
site:*.target.com
Outside quotes: forces Google to show subdomain results explicitly — wildcard subdomain enumeration pattern.
N..M
N..M  (number range)
Modifier → Matches any number within the specified inclusive range
Range

Two dots between two numbers (N..M) define a numeric range. Google will match any value between the lower and upper bound, inclusive. Useful for CVE years, version numbers, prices, and port numbers in exposed service banners.

Format: No spaces around the dots — 2020..2024 not 2020 .. 2024. Can be combined with other operators freely.

Security use cases: Filter vulnerability disclosures by year range, find version-specific software exposures, or narrow hardware recon by model year.

Usage Patterns — Numeric Targeting
CVE 2020..2024 filetype:pdf site:target.com
Finds CVE-referencing PDF documents on the target from years 2020 through 2024 — good for security audit reports.
intext:"Apache/2.2..2.4"
Find Apache version banners in the 2.2–2.4 range exposed in server error pages or directory listings.
site:target.com intext:"version 1..9"
Finds pages that display a version number from 1 to 9 — useful for application version fingerprinting.
05 — Combining Operators

The Real Power Is in Chaining

No single operator is very powerful alone. Effective dorks combine multiple operators to triangulate exactly what you're targeting — each operator constraining a different layer simultaneously.

Mental Model for Combining
Each operator adds a constraint on a different layer. One constraint = broad. Three constraints = surgical. Think of it like an AND filter: site: (domain) AND intitle: (title) AND inurl: (path) AND filetype: (type) = very specific target.
Example 01 Find exposed admin login panels on a target domain
intitle:"Admin Login"  inurl:/admin/  site:target.com
intitle:"Admin Login"
The <title> tag must contain the phrase "Admin Login" — confirms it's an admin page.
inurl:/admin/
URL must contain /admin/ path — confirms the endpoint structure.
site:target.com
Restrict all results to target.com only — no other domains.
Example 02 Find exposed .env files with database credentials
filetype:env  intext:"DB_PASSWORD"  intext:"DB_HOST"
filetype:env
Only return .env files — immediately filters to environment config files.
intext:"DB_PASSWORD"
File must contain the string DB_PASSWORD in its body text.
intext:"DB_HOST"
Also must contain DB_HOST — together these confirm it's a database configuration file.
Example 03 Enumerate SQLi-candidate pages on a target
site:target.com  inurl:"?id="  intext:"Welcome"
site:target.com
Scope limited to target domain only.
inurl:"?id="
URL contains an integer parameter — common SQLi vector. The id= suggests database query based on user input.
intext:"Welcome"
Page renders "Welcome" text — suggests it's an authenticated or dynamic page responding to the id parameter.
Example 04 Find exposed Git repositories
intitle:"index of /.git"  intext:"HEAD"
intitle:"index of /.git"
Title tag shows a directory listing of a .git folder — the repo is publicly browsable.
intext:"HEAD"
Page body contains "HEAD" — confirms it's a real Git directory with the HEAD ref file visible.
Example 05 Multi-TLD subdomain recon with noise filtering
(site:target.com OR site:target.io OR site:target.net)  -www -inurl:blog -inurl:help
(site:target.com OR site:target.io OR site:target.net)
Logical OR across three TLDs in one query — covers the full domain portfolio of a target organization.
-www -inurl:blog -inurl:help
Minus exclusions strip the main public-facing pages — what remains are subdomains, dev environments, and internal tools.
Example 06 Exposed config files — multiple extensions in one query
(filetype:env OR filetype:yml OR filetype:conf)  intext:"password"  -site:github.com -site:stackoverflow.com
(filetype:env OR filetype:yml OR filetype:conf)
Covers three config file types simultaneously — environment, YAML, and generic conf files.
intext:"password"
The word "password" must appear in the file body — filters to credential-bearing config files.
-site:github.com -site:stackoverflow.com
Excludes the two largest sources of noisy false positives — code repos and Q&A sites with example configs.
Example 07 Wildcard directory enumeration — all folder names
intitle:"index of *"  site:target.com  -inurl:wordpress -inurl:wp-content
intitle:"index of *"
Wildcard matches any directory listing regardless of folder name — "index of /uploads", "/backup", "/api", "/private", etc.
site:target.com
Scoped to the target domain — all directory listings across every subdomain.
-inurl:wordpress -inurl:wp-content
Filters out WordPress plugin and theme directories — the most common false positive in open directory queries.
Example 08 Private key exposure — exact phrase in any file type
"-----BEGIN RSA PRIVATE KEY-----"  (filetype:pem OR filetype:txt OR filetype:key)  -site:github.com
"-----BEGIN RSA PRIVATE KEY-----"
Exact PEM header — this precise string only appears in real RSA private key files. Quotes ensure exact matching.
(filetype:pem OR filetype:txt OR filetype:key)
Covers three extensions private keys are commonly saved as — ensures we don't miss any.
-site:github.com
Excludes GitHub — the single largest source of noisy test/example private keys that dilute real findings.

07 — Common Mistakes

What Goes Wrong and Why

These are the exact mistakes most beginners make. Each one is explained with a wrong/right example so you can immediately see the difference.

⚠
Confusing intitle: with searching the visible h1 heading
intitle:admin
Thinking this searches the <h1> "Admin Panel" visible on the page
intitle:admin
This searches the <title> tag — browser tab text only. Use intext: for visible headings.

The <title> and <h1> are completely different HTML elements. The title lives in <head> and shows in the browser tab. The h1 is a visible heading inside the page body. intitle: only reads the title tag. To search visible headings, use intext:.

⚠
Using intitle: when you need inurl:
intitle:/wp-admin/
Trying to find WordPress admin by path — won't work reliably
inurl:/wp-admin/
URL path is what inurl: is for — correct and effective

If you want to find a specific directory or path, use inurl: — that's exactly what it's for. intitle: doesn't read URLs. Use each operator for its designated layer.

⚠
Misunderstanding intitle: with multiple words
intitle:admin login panel
Thinking all 3 words must be in the title
allintitle:admin login panel
Use allintitle: when you want all words in the title

With intitle:admin login panel, only "admin" is locked to the title. "login" and "panel" are searched anywhere on the page. To force all three into the title, use allintitle:admin login panel.

⚠
Confusing inanchor: with inurl: — link text vs. link destination
inanchor:/admin/login
Trying to find pages linking to /admin/login by href
inurl:/admin/login
inurl: searches the URL. inanchor: is for the link's visible label text.

inanchor: reads the text you click on — like "Click here to login". It does not read what URL the link points to. For link destinations, the URL is part of the page's source, not its anchor text — use inurl: for paths.

⚠
Forgetting that intext: alone is rarely useful — combine it
intext:password
Returns millions of results — too broad to be useful
intext:"DB_PASSWORD" filetype:env
intext: + filetype: = specific, actionable results

Google already searches body text by default. intext: alone does almost nothing new — it's redundant for simple searches. Its value is in being combined: lock a keyword to the body while using filetype:, inurl:, or site: to narrow the scope.

⚠
Writing OR in lowercase — it becomes a search keyword, not an operator
site:gov or site:mil filetype:xls
Lowercase "or" — Google treats it as a search word, ignores it as an operator
site:gov OR site:mil filetype:xls
Uppercase OR — Google treats it as a logical operator, returns results from either domain

OR must be fully uppercase. With lowercase "or", Google either ignores it or treats it as a literal search keyword. The pipe | is a reliable alternative that doesn't have capitalization ambiguity: site:gov | site:mil.

⚠
Using * outside quotes expecting wildcard subdomain or path matching
intitle:index of * backup
Wildcard outside quotes — doesn't work as intended. * is literal outside quotes.
intitle:"index of * backup"
Wildcard inside quotes — * matches any single word in that position within the phrase

The * wildcard only works as a word placeholder inside double-quoted phrases. Outside quotes, it is treated as a literal asterisk. Additionally, * inside quotes matches exactly one word — not zero words or multiple words. "index of * backup" works; intitle:index of * backup does not.

⚠
Forgetting quotes on filetype: ext: values with special characters
filetype:env intext:DB_PASSWORD=
The = at the end may be misinterpreted — inconsistent behavior
filetype:env intext:"DB_PASSWORD="
Quoted phrase including the = ensures exact assignment pattern match

Config key patterns like DB_PASSWORD=, SECRET_KEY=, and PRIVATE_KEY= should always be quoted. The = character has special meaning in some query contexts. Quoting the whole pattern also ensures you're finding the variable assignment form, not just any page that mentions the keyword anywhere.

⚠
Using filetype: and ext: on the same query expecting stricter filtering
filetype:env ext:env intext:password
Thinking two operator variants = stricter filtering — they're identical
filetype:env intext:password
One is enough — ext: and filetype: return the same results

filetype: and ext: are exact aliases — they are processed identically by Google. Using both in one query does not add any additional restriction. Pick one and use it consistently. Use OR with both only if you're trying to cover two different file types: filetype:env OR filetype:conf.

⚠
Placing - (minus) with a space before the keyword — it won't exclude
site:target.com - inurl:blog
Space between - and the operator — "- inurl:blog" becomes a literal minus sign in the query
site:target.com -inurl:blog
No space — the minus must immediately precede the operator or keyword

The exclusion minus - must be written with no space before the term. -inurl:blog excludes results with "blog" in the URL. - inurl:blog (with a space) is parsed as a regular hyphen and ignored as an exclusion operator. This is one of the most common reasons exclusions silently fail.
