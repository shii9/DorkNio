01 — Introduction

What is Google Dorking?

Google Dorking (also called Google Hacking) is the practice of using advanced Google search operators to uncover specific — often sensitive — information that has been inadvertently indexed by Google's web crawler. The technique was popularized by security researcher Johnny Long, who compiled thousands of effective queries into the Google Hacking Database (GHDB) starting in the early 2000s.

Google's crawler continuously indexes the public web — including misconfigured servers, exposed directories, leaked credentials, unprotected admin panels, and sensitive documents that were never meant to be publicly accessible. Google Dorking is the art of querying that index with precision.

KEY INSIGHT: Google Dorking does not "hack" anything directly. It leverages Google's existing index to surface information that is technically public but accidentally exposed. No target systems are touched — all queries run against Google's own database.
⚠ LEGAL WARNING: Running Google Dorks against targets without explicit written authorization may violate the Computer Fraud and Abuse Act (CFAA), GDPR, or local cybercrime laws. This guide is strictly for authorized security testing, bug bounty programs, defensive awareness, and academic study.

Why It Matters for Pentesters

In a real penetration test — and on eJPT / OSCP exams — the reconnaissance phase relies heavily on OSINT. Google Dorking can reveal attack surface, sensitive data, technology stack details, and vulnerable files, all without touching the target.

Attack Surface

Exposed login pages, admin panels, VPN portals, and remote access interfaces that expand entry points.

Sensitive Data

Leaked credentials, API keys, database dumps, .env files, and config files left in the open.

Technology Stack

Server versions, CMS platforms, frameworks — cross-reference with CVEs for known exploits.

Vulnerable Files

Open directory listings, exposed .git folders, unprotected .env files, and backup files.

Third-Party Leaks

Credentials leaked on GitHub, Pastebin, Trello, or code-sharing sites referencing your target.

Zero Infrastructure Touch

100% passive — no packets sent to target. Perfect for the passive recon phase of any engagement.

02 — Core Operators

Core Search Operators

These are the fundamental building blocks of every Google Dork. Each operator tells Google exactly where to look for your keyword — in the URL, title, body, domain, or file type. Master these before combining them.

site:
Restricts all results to a specific domain or subdomain. The most-used operator in pentest recon. Does not search sub-paths unless combined with other operators.
intitle:
Finds pages where the HTML <title> tag contains the specified keyword. Useful for finding admin panels, login pages, and error pages.
allintitle:
All specified words must appear in the page title. More restrictive than multiple intitle: calls.
inurl:
Finds pages where the URL contains the specified string. Great for finding specific paths, parameters, or scripts.
allinurl:
All specified words must appear in the URL. Narrows results further than multiple inurl: calls.
intext:
Finds pages where the visible body content contains the specified keyword. Useful for error messages, passwords in page content, and leaked data.
allintext:
All specified words must appear in the body content. More targeted than multiple intext: operators.
filetype:
Finds indexed files of a specific type — pdf, xls, xlsx, docx, txt, log, sql, env, conf, bak, pem, and more.
ext:
Exact alias for filetype: — both work identically. Finds files by extension.
cache:
Shows Google's cached (snapshot) version of a URL. Useful when the original page has been taken down or modified since indexing.
related:
Finds websites topically similar to a given URL. Useful for competitor/infrastructure mapping.
info:
Shows Google's info summary about a specific URL — cached version, similar pages, linking pages.
"exact phrase"
Quotation marks force an exact phrase match. Critical for finding specific error strings, credential patterns, and configuration snippets.
-keyword
Minus sign excludes results containing a keyword. Essential for filtering noise from broad queries.
OR  /  |
Logical OR — returns results matching either term. Example: site:gov OR site:mil
* (wildcard)
Matches any word in a phrase. Example: "index of *" matches any directory listing.
.. (range)
Number range operator. Example: camera $200..$500 finds cameras in that price range.

Basic Operator Examples

Enumerate all indexed pages of a target:

site:example.com// Shows everything Google has indexed from this domain — your baseline

Discover subdomains (passive):

site:*.example.com -www// Wildcard subdomain enumeration — exclude www to surface forgotten assets

Find admin/login pages by title:

intitle:"admin login" site:example.com// Pages whose HTML title contains "admin login" on the target domain

Find URL paths containing "admin":

inurl:admin site:example.com// Any URL under example.com containing /admin/

Exact string in page body:

intext:"Index of /" site:example.com// Body contains that exact string — classic open directory indicator

Find a specific file type:

filetype:pdf site:example.com// All PDF files indexed from example.com

Exclude noise with minus:

site:example.com -inurl:blog -inurl:news// Show all pages except blog and news sections
03 — Advanced Operators

Advanced Operator Techniques

These patterns go beyond simple lookups, targeting specific structural indicators that signal misconfiguration, version leakage, or exposed infrastructure.

INURL — URL Pattern Hunting

inurl:/wp-admin/ site:example.com// WordPress admin panel — brute-force candidate if found exposed
inurl:"/phpMyAdmin/" intitle:"phpMyAdmin"// Exposed phpMyAdmin database management interfaces
inurl:":8080" OR inurl:":8443" site:example.com// Non-standard ports — frequently dev/test servers with weaker auth
inurl:"/cgi-bin/" site:example.com// CGI script directories — historically Shellshock-vulnerable
inurl:".php?id=" site:example.com// Pages with ?id= parameter — prime SQLi injection test targets
inurl:"/api/v1/" OR inurl:"/api/v2/" site:example.com// API versioned endpoints — check for unauthenticated access

INTITLE — Page Title Patterns

intitle:"index of" "parent directory"// Classic open/exposed directory listing on misconfigured web servers
intitle:"Dashboard" inurl:"/dashboard" site:example.com// Application dashboards — may be accessible without authentication
intitle:"Cisco System" inurl:"/exec/show"// Exposed Cisco router management — can show running config
intitle:"Network Camera" inurl:"/view.shtml"// IP cameras with publicly accessible live streams
intitle:"Apache Tomcat" "Error report"// Tomcat error pages leaking version, OS, and file path information
intitle:"Welcome to nginx"// Nginx default install pages — server may be misconfigured or abandoned
intitle:"Laravel" intext:"APP_DEBUG=true"// Laravel apps with debug mode ON — full stack trace exposed to public

INTEXT — Body Content Patterns

intext:"sql syntax near" OR intext:"syntax error has occurred" OR intext:"mysql_fetch"// Raw SQL error messages — strong indicator of SQLi vulnerability
intext:"Warning: mysql_connect()" intext:"on line" site:example.com// PHP MySQL connection errors leaking DB hostname and credentials path
intext:"ORA-01756" OR intext:"ORA-00942"// Oracle database error codes leaking schema information
intext:"Traceback (most recent call last)" site:example.com// Python/Django uncaught exceptions leaking file paths and code
intext:"powered by" intext:"phpBB" site:example.com// Technology fingerprinting via footer attribution

CACHE — Accessing Removed Content

cache:example.com/admin/config// View Google's cached snapshot of a page that may now be deleted/secured
cache:example.com/backup.sql// Access a cached version of a database file that was briefly exposed
04 — Combining Operators

Combining Operators — Power Dorks

Single-operator dorks are broad. The real precision comes from chaining multiple operators together. Each additional constraint narrows results, surfacing highly specific exposed resources.

SYNTAX RULE: Operators are separated by spaces. No comma, no semicolon. Chain as many as needed on one line:
site:example.com filetype:sql intitle:"backup" intext:"password"

Exposed Credentials & Secrets

site:example.com filetype:env "DB_PASSWORD"// .env files containing database credentials — critical severity
site:example.com filetype:log intext:"password"// Application log files containing plaintext passwords
site:example.com filetype:yml intext:"password:"// YAML config files (Docker Compose, CI/CD) with hardcoded passwords
site:example.com inurl:"config" filetype:php intext:"password"// PHP config files containing credential variables
site:pastebin.com "example.com" "password"// Leaked credentials pasted on Pastebin referencing the target domain
filetype:sql intext:"INSERT INTO" intext:"password"// SQL dumps containing user tables with password hashes or plaintext

Exposed Git Repositories

inurl:/.git/ intitle:"Index of /.git"// Exposed .git directory — entire source code + commit history + secrets accessible
inurl:"/.git/config" site:example.com// Git config file — reveals remote URL, branches, and sometimes credentials

Open Directory Listings

intitle:"index of" "backup" site:example.com// Backup files sitting in open web-accessible directories
intitle:"index of" ".sql" OR ".db" site:example.com// Raw database files in browseable directories
intitle:"index of" "config" site:example.com// Configuration files in open directories
intitle:"index of" ".bak" OR ".old" site:example.com// Backup versions of files — may contain old unpatched code
intitle:"index of" "/uploads/" site:example.com// Unprotected file upload directories — check for webshells

Admin & Login Panels

site:example.com inurl:admin intitle:"login"// Admin login portals on the target domain
site:example.com inurl:"/wp-login.php"// WordPress login pages — test for default/weak credentials
site:example.com inurl:"/administrator/index.php"// Joomla CMS administrator login
site:example.com intitle:"Webmin" inurl:":10000"// Webmin server admin interface on default port 10000
site:example.com inurl:"/panel/" OR inurl:"/cpanel/" intitle:"login"// Control panels and hosting management interfaces

Network Devices & IoT

intitle:"RouterOS" inurl:"/winbox/"// MikroTik routers with exposed WinBox web interface
intitle:"AXIS" inurl:"/mjpg/video.mjpg"// Axis network camera live MJPEG streams — publicly viewable
intitle:"D-Link" inurl:"/login.cgi"// D-Link router admin login pages
intitle:"Hikvision" inurl:"/doc/page/login.asp"// Hikvision IP security camera admin panels

Error Messages & Version Leaks

site:example.com intext:"fatal error" OR intext:"stack trace" OR intext:"Traceback"// Application exceptions leaking file paths, code, and infrastructure info
site:example.com intitle:"Apache/2" "Server at"// Apache default pages showing exact server version and OS details
site:example.com intext:"PHP Version" intitle:"phpinfo()"// Exposed phpinfo() pages — full PHP config, loaded modules, environment vars

Vulnerable Parameter Discovery

07 — Pentest Recon

Google Dorking Recon Workflow

In a structured penetration test, Google Dorking sits in the passive reconnaissance phase — before any active scanning or enumeration. Here is a 6-phase systematic approach used by professional pentesters and bug bounty hunters.

1
Surface Mapping — Understand the Target's Footprint

Start broad. Understand how much of the target is indexed, what the domain structure looks like, and what Google knows about it.

site:example.com// Baseline: how many pages indexed? What's the app structure?
site:*.example.com -www// Subdomain enumeration — dev, staging, old, internal subdomains
info:example.com// Google's info summary — links to cached version, related pages
related:example.com// Similar/related sites — may share infrastructure or developer teams
2
Technology Fingerprinting — Identify the Stack

Identify CMS, frameworks, server software, and versions. Each technology fingerprint is a pivot point to known CVEs.

site:example.com intext:"Powered by"// Technology attribution in page footers
site:example.com inurl:"/wp-content/" OR inurl:"/wp-includes/"// WordPress — then enumerate plugins: inurl:"/wp-content/plugins/"
site:example.com intitle:"phpinfo()"// Exposed phpinfo() pages — gold mine of server configuration data
site:example.com "Server at" intitle:"Apache"// Apache default pages showing version and OS
3
Login & Admin Panel Discovery

Find every authentication point — admin consoles, VPN portals, API authentication endpoints, remote management interfaces.

site:example.com intitle:"login" OR intitle:"sign in"// All login pages on the domain
site:example.com inurl:admin OR inurl:administrator OR inurl:backend OR inurl:portal// Admin and backend interfaces
site:example.com inurl:dashboard OR inurl:panel OR inurl:cpanel// Control panels and monitoring dashboards
site:example.com inurl:":4443" OR inurl:":8443" OR inurl:":8080"// Non-standard port admin interfaces — often less secured
4
Sensitive File Discovery

Hunt for accidentally exposed configuration, database, log, and backup files.

site:example.com filetype:env OR filetype:log OR filetype:sql OR filetype:bak OR filetype:conf// One combined query sweeping all common sensitive file types
site:example.com intitle:"index of" -html -htm -php -asp// Open directories containing non-web files (databases, configs, archives)
site:example.com inurl:backup OR inurl:archive OR inurl:old// URLs with backup/archive paths — common developer oversight
5
Vulnerability Parameter Hunting

Find injectable parameters and potentially vulnerable input vectors for SQLi, XSS, LFI, and open redirect testing.

site:example.com inurl:"?" inurl:"="// Any page with GET parameters — broad sweep of injection candidates
site:example.com inurl:"?id=" OR inurl:"?page=" OR inurl:"?item="// Integer-based parameters — highest SQLi potential
site:example.com inurl:"?file=" OR inurl:"?path=" OR inurl:"?dir="// File path parameters — LFI/RFI candidates
site:example.com inurl:"?url=" OR inurl:"?next=" OR inurl:"?redirect="// Redirect parameters — open redirect and SSRF candidates
6
Third-Party Leak Discovery

Search developer collaboration tools, code hosting platforms, and paste sites for accidental credential exposure.

site:github.com "example.com" "password" OR "token" OR "secret" OR "api_key"// GitHub code leaks associated with target domain
site:pastebin.com "example.com"// Paste site content referencing the target
site:trello.com "example.com"// Public Trello boards containing target references
site:s3.amazonaws.com "example.com" OR site:blob.core.windows.net "example"// Public cloud storage buckets associated with target
08 — Defense

Defending Against Google Dorking

Understanding how to attack via Google Dorks also makes you a better defender. These are the techniques used to prevent accidental information exposure on Google's index.

robots.txt

Instruct crawlers not to index sensitive paths. Note: robots.txt is publicly readable — it tells attackers exactly what you're hiding. Use as defense-in-depth.

User-agent: * Disallow: /admin/ Disallow: /config/ Disallow: /backup/ Disallow: /.git/
Meta Noindex Tag

Prevent Google indexing sensitive pages even if crawled — add to every admin/config page's HTML head.

<meta name="robots" content="noindex, nofollow">
X-Robots-Tag Header

For non-HTML files (PDFs, docs), use the HTTP response header to signal noindex — meta tags don't work in binary files.

X-Robots-Tag: noindex, nofollow
Google Search Console

Monitor what's actually indexed on your domain. Submit URL removal requests for sensitive pages. Use the Coverage report to audit all indexed content.

Proper Access Controls

Never rely on obscurity. Sensitive admin panels and files must require authentication regardless of whether they're indexed. Require MFA on all admin portals.

.gitignore Hygiene

Prevent credential commits at the source. Add these to every project:

.env *.log config.php *.pem *.key *.p12 database.yml
Web Server Config

Disable directory listings. Suppress version disclosure in headers. Remove default pages like phpinfo.php and server test pages.

# Apache Options -Indexes # Nginx autoindex off; server_tokens off;
Regular Dork Audits

Run Google Dorks against your own domain on a scheduled basis as part of continuous security monitoring. Find what attackers find, before they do.

Audit Your Own Domain — Defensive Dorks

site:yourdomain.com filetype:env OR filetype:log OR filetype:sql OR filetype:bak OR filetype:conf// Check for any exposed sensitive files in Google's index
site:yourdomain.com intitle:"index of"// Check for any open directory listings
site:yourdomain.com intext:"DB_PASSWORD" OR intext:"mysql_connect" OR intext:"PRIVATE KEY"// Check for accidentally indexed credential content
site:github.com "yourdomain.com" password OR token OR secret OR api_key// Check for developer credential leaks on GitHub
site:pastebin.com "yourdomain.com"// Monitor paste sites for content about your domain

⚠ RATE LIMITING: Google will temporarily block your IP if you run too many automated dork queries rapidly. You'll see a CAPTCHA. Mitigations: use a VPN with rotation, add 10–30 second delays, use pagodo with the --delay flag, or use the Google Custom Search API (100 free queries/day) for automated workflows.
